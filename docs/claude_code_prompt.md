## Ground rules

1. **Do not invent values for open items.** `CLAUDE.md` lists seven. Where one blocks you, write the code path, raise a clear `NotImplementedError` or read from a config key that doesn't exist yet, and tell me. Do not substitute a plausible default. Several parameters in this project look guessable and are not.
2. **Every presence pull must assert** — non-empty result, exactly one distinct IMO matching the expected vessel, observed hours within tolerance of elapsed hours. A wrong ship name returns HTTP 200 with zero rows and no error; this is the project's most dangerous failure mode.
3. **Key everything on the IMO number.** GFW's `vesselId` fragments — one hull has several.
4. **Sequential API calls only.** One concurrent 4Wings report is permitted; more returns 429.
5. **No vessel-specific values in code.** They belong in `config/`. Scaling from two vessels to the fleet must be a loop over an IMO list, not an edit.
6. Every estimated parameter carries `value`, `source` and `method` fields, so a researcher with IHS access can substitute observed values without touching model code.

## Architecture

Python owns API access, parsing and the physical model. DuckDB owns spatial joins, aggregation, allocation and reporting. The dividing principle, already decided: **lookups, joins, windows and aggregations are SQL; physical formulas are Python.**

Put SQL in `.sql` files under `src/emissions_allocation/sql/`, loaded by name — not embedded in Python string literals. The SQL is a deliverable in its own right and should be readable on its own.

Proposed layout; adjust if the workflow argues for something better, but tell me what you changed and why:

